# 调试报告：崩溃现场常开 —— 桥 139 死从此有据可查（2026-10-05）

## 一、为什么要做这件事

两条老任务一直查不动，卡点是同一个：

- **#42** 壳的 Go 代理自更新在 x86_64 guest 里打死 ART（`[GoProxy] start failed` 紧跟 `退出码=139`）
- **#46** `op=host categoryContent` 触发的 `s=11 pc=…fb17`

宿主日志里的数字说明了问题：**`[sig]` 现场行 0 条，而 `退出码=139` 有 5 次**。
崩溃发生了，一点现场都没留 —— 没有 PC、没有故障地址、没有落在哪个模块，任何归因都只能是猜测。

### 先更正我上一轮的一句错判

我在《网盘对话框不刷新》报告收尾时说过"桥自己**没有**崩溃处理器"。**这句是错的**，
因为当时只 grep 了 `proppreload.c`。真相是：处理器一直都有，在 `art/artlaunch.c` 里
（`sig_trampoline` + 自制 libsigchain 的 `SetSpecialSignalHandlerFn`），
只是被 `CATCLAW_SIGLOG` 环境变量挡住了，生产开机没人设过它。
所以这次不是"加一个处理器"，而是**把它常开，并把它该去的地方改掉**。

## 二、为什么它原来是关的（以及为什么那个理由不该继续成立）

`artlaunch.c` 里的原注释写得很清楚：默认关是因为**宿主握手期 console 管道没人读**，
ndk 转译 fault 的 SIGSEGV 是高频信号，`write` 很快写满 64KB 管道 → 阻塞在信号处理里 →
guest 全线程冻住 → 探针永远 ping 不通（2026-09-27 WHPX 实锤）。

这个理由是**真的**，但它证伪的是"往 stderr 写"，不是"要留现场"。于是：

| | 原来 | 现在 |
|---|---|---|
| 现场去处 | 只有 stderr（会被写满） | **持久盘上的文件** `/data/catclaw/sig-crash.log`，stderr 只留前 6 行指路牌 |
| 开关 | `CATCLAW_SIGLOG=1`，生产不开 | init 里**常开** |
| 预算 | 无（所以只能关） | 每进程 400 行；预算用完**连那次 256KB 的 `/proc/self/maps` 读都跳过**，并留一行"预算用完" |
| 防刷爆盘 | — | 启动时 >256KB 先改名让路（改名不清空：清空会把刚要查的那次一起清掉） |

之所以文件路线现在**才**可行：`/data` 从 2026-10-05 起是持久 ext4 数据盘（见《网盘登录持久化》
报告）。桥 139 死掉之后，init 监督器原地重启桥（VM 与 /data 不动），宿主再用生产入口
`op=readfile` 就能捞到**上一次崩溃**的现场。现场因此跨进程、跨开机存活。

另外补了**兜底注册**：`CreateJavaVM` 之前的原生段没人经 libsigchain 注册，那一段崩了是无声 139；
现在只对当前是 `SIG_DFL` 的 SIGSEGV/SIGBUS/SIGABRT/SIGFPE 占位，不抢任何已装 handler，
ART 之后照常进链（"后注册者先处理"的语义不变）。

## 三、自检：让"现场链路"变成可控实验

自然崩溃等不来就只能永远没判据。加了 `CATCLAW_SIGTEST=<秒>`：到点在桥自己的进程里做
一次**真**空指针写（`volatile int *p = NULL; *p = 1;`），走的是与真崩溃完全相同的路径
（trampoline → 链上无人处理 → `_exit(128+11)` → 监督器重启）。生产 init 不带这个变量。

同时把自检状态写进**启动标记行**：`[sig] --- artlaunch 启动 pid=af（十六进制）自检=无 ---`。
没有这个标记，日志里自检造出来的现场和真崩溃现场长得一模一样 —— 那是会误导后人的。

## 五、一个反直觉的观察（会误导人，先记下来）

两次自检现场跑的是**同一条指令**（PC 偏移都是 `0x2903`），si_code 却一次 `c=1`（SEGV_MAPERR）
一次 `c=0`。含义：**在这个 guest 里 `c=0` 不能当成"信号是外部 kill 进来的"的证据**。
机理还没查（可能与非 Java 线程的 ART FaultManager 处理路径有关），但判据先修正：
只有 `s=…` 而拿不到 fault 现场时别急着甩锅给外部信号。

## 六、出包过程踩到的坑

1. **`/artlaunch` 与 `/system/bin/artlaunch` 是 initrd 里的两条条目，init 起的是后者**。
   只换一条 = 换了个寂寞。`mk_x86_initrd.sh` 里那两行 `cp` 就是为这件事写的。
   ⇒ 新工具 `tools/initrd/replace_initrd_entries.py`（一次过换多条 + 查无条目就整体不写），
   以及 `tools/initrd/dump_initrd_entry.py`（注入前先 dump 比对，`--check` 直接判相符）。
2. **部署包里的 `/init` 比仓库脚本多了 crc16 修复**（314 字节差异，全是上一轮那处修复）——
   照仓库脚本重新生成 `/init` 就会把持久盘的修复倒回去。本次已把仓库脚本**收敛到部署包内容**
   再叠加新开关，两边现在同源。
3. **pid 进制不一致**：启动标记用十进制（`pid=263`），现场行用十六进制（`p=107`），
   同一个进程看着像两个，白查一轮。⇒ 统一十六进制并当场标注"（十六进制）"。
4. **泵的应答是 JSON，`+` 被转义成 `\u002B`**（System.Text.Json 默认 HTML 转义）。
   用正则截 base64 会截断并报"cannot be 1 more than a multiple of 4"。⇒ 必须走 JSON 解码。
5. 老结论"`SIGLOG` 只能默认关"是把 stderr 的限制当成了需求本身 —— 已在代码注释里改写。
