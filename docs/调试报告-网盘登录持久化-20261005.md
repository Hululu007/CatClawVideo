# 定因与修复｜Windows 端网盘登录无法持久化（2026-10-05）

> 现象（用户反馈）：夸克扫码成功、能播，但**应用重启后网盘页显示"未登录"**。
> 日志里能直接看到这个翻转：`23:34:01 … 夸克网盘 … "已登录"` → 重启 → `23:59:08 … "未登录"`。

## 一、一句话结论

**持久数据盘一直是好的，坏的是挂载它的那一步**：initrd 里的 `/init` 少加载了一个 `crc16` 内核模块，
导致 `ext4.ko` 装不上 → `mount -t ext4` 报 `No such device` → `/data` 静默退回 tmpfs →
插件写在 `/data` 里的**登录令牌文件**每次冷启全丢。宿主为此准备的"偏好回灌"只搬 `shared_prefs/*.xml`，
搬不到令牌文件，于是表现为"cookie 还在（能播）、令牌死了（未登录）"。

第二处缺陷让修复在宿主侧被抵消：宿主判断"`/data` 是否真持久"时读串口日志，
**只要历史里出现过 `fsck 后 mount RC=` 就优先用它** —— 而串口日志跨开机累加，
上一次开机失败的残留 `255` 会把这次成功的 `RC=0` 盖掉，于是宿主误判"不持久"，
照样跑回灌，把刚挂上的持久盘**倒回**成宿主的旧副本。

## 二、证据链（每步都是实测，不是推断）

### 2.1 盘是好的，挂载失败是驱动缺失

修复前（同一次开机，串口日志）：

```
[persist] 盘节点: /dev/vdc; 内核 ext4 支持: 0（0=无!）; partitions:
 254  32  16777216 vdc                      ← 16 GiB 盘在，节点在
[persist] 预挂载 fsck rc=0 尾行: /dev/vdc: clean, 338/1048576 files, 285922/4194304 blocks
                                            ↑ e2fsck 读得懂 = 盘上是健康 ext4，且里面有 338 个文件
mount: mounting /dev/vdc on /data failed: No such device
[persist] mount RC=255                       ← ENODEV = 内核没有这个文件系统驱动，不是盘的问题
```

### 2.2 缺的就是 crc16

| 事实 | 来源 |
|---|---|
| `modinfo -F depends ext4.ko` = `jbd2,mbcache,`**`crc16`** | 108 上 `/root/b1_blobs/ko/…/kernel/fs/ext4/ext4.ko` |
| `modules/crc16.ko` **在** initrd 里（6025B） | 解包 `art_initrd_x64.gz`（2228 条目）逐个列出 |
| 部署版 `/init` 的加载列表 = `crc32c_generic jbd2 mbcache ext4 binfmt_misc` —— **没有 crc16** | 解包取出的 `/init`（10176B）第 19 行 |
| 因此 guest 只打了 `insmod jbd2/mbcache/ext4/binfmt_misc` 四行，`ext4` 那行报 `unknown symbol in module` | 开机日志 |
| 仓库里那份带持久盘段的脚本 `init_x86.guest-good-20261002.sh:27` 列表**是对的**（含 crc16） | 直接读 |

⇒ **产物漂移**：打包进 initrd 的 `/init` 不是那份带持久盘段的正确脚本，而是中间版本。
⚠ 为什么 git 看不见这次漂移：2026-10-03 做了**三仓库拆分**（`.gitignore:500-512`），
`JavaBridge/src`、`JavaBridge/qemu-src`、`CatClawVideo.Maui/QemuGuest/` 全部迁到兄弟仓库
**`CatClaw.Qemu`**（本机在 `D:\Code\CatClaw.Qemu`，桩源码是 `guest/java/src/`，
initrd 作为 GitHub Release 附件 `vm-assets-v1` 由 `tools/fetch-assets.ps1` 取回）。
本仓库里这些路径只是**本地副本**，所以"本仓库里是对的"根本不等于"跑起来是对的"。

### 2.3 令牌确实是"文件"，且落在同步范围之外

guest 自己的 `datawatch` 清单（每 20s 变化时全量上报）显示，插件在 `/data/cache` 写了：

| 文件 | 大小 | 宿主是否同步 |
|---|---|---|
| `/data/cache/data_IDbd` | 10 B | **否** |
| `/data/cache/.ftyfnwnqdsew8dmg` | 102 KB | **否** |
| `/data/cache/sharedb/*`、`/data/cache/pvc/` | — | 部分（只上行 xml 那批） |
| `/data/catclaw/shared_prefs/*.xml` | 11 个 | 是（prefs-sync / file-sync 两条通道） |

宿主侧 `guest-prefs/` 与 `guest-prefs/sharedb/` 里**只有那 11 个 xml**，没有任何
`data_IDbd` / `.ftyfnw*` —— 与桥源码里 2026-10-01 就写下的判断一致
（`JavaBridge/src/bridge/Server.java:1319`："令牌是**文件**…宿主只同步了 `shared_prefs/*.xml`，
于是 cookie 活着（能播）、令牌死掉（界面显示未登录）"）。

## 三、改了什么

| # | 位置 | 改动 |
|---|---|---|
| 1 | initrd 内 `/init`（产物） | 模块列表补 `crc16` 并放到依赖正确的位置：`crc16 crc32c_generic mbcache jbd2 ext4 binfmt_misc` |
| 2 | `CatClawVideo.Maui/Providers/JavaSpiderRuntime.cs` `IsGuestDataPersistentAsync` | 判定改为"**两条标记谁在日志里更靠后就以谁为准**"，不再无条件优先 `fsck 后` 那条 |

改动 1 用 `tools/initrd/replace_initrd_entry.py`（本次新写，与 `JavaBridge/qemu-src/tools/x86guest/append_initrd.py`
互补：那个只能追加，这个整包重建）替换 `init` 一个条目：
替换前后条目数都是 2228、名字序列完全一致、内容变化的条目只有 `init`（10176B → 10490B）。

> 写这个工具时踩到一个必须记住的坑：newc 头的 `namesize` **包含结尾 NUL**。
> 第一版按 `len(name)` 写，解包时每个名字都被截掉最后一个字符（`init` → `ini`），
> 幸好在写回前用"重新解析一遍并比对条目"的自检抓出来了。

## 五、还剩哪一步确认（写清楚，不含混）

- **扫码 → 重启 → 仍显示"已登录"** 这条端到端只能由用户扫一次码完成。
  机制层面导致它失败的环节（令牌文件随 tmpfs 消失）已按上表证死并修好；
  但"新登录一次能留住"这句话，需要一次真实扫码来盖章。
- 盘上现存的 10-03 状态是否仍被夸克服务端接受（令牌可能已过期），本次无法判定；
  过期会表现为"仍未登录"，但那是**令牌寿命**问题，不再是**持久化**问题。

## 六、发布面必须做的一件事（否则别的机器还会坏）

`QemuGuest/` 是 gitignore 的产物目录，所以**修好的 `/init` 不会随 git 分发**。
出包/装包时必须保证 initrd 里的 `/init` 与仓库脚本
`JavaBridge/qemu-src/tools/x86guest/init_x86.guest-good-20261002.sh` 同源（含 `crc16`）。
自检命令（不需要跑 VM）：

```bash
python - <<'EOF'
import gzip, sys
sys.path.insert(0, "tools/initrd")
from replace_initrd_entry import parse
b = gzip.decompress(open("CatClawVideo.Maui/QemuGuest/x86guest/art_initrd_x64.gz", "rb").read())
i = [e[2].decode("utf-8", "replace") for e in parse(b) if e[1].lstrip("./") == "init"][0]
print([l.strip() for l in i.splitlines() if "for m in" in l and "ext4" in l])
EOF
```

看到 `for m in crc16 crc32c_generic mbcache jbd2 ext4 binfmt_misc; do` 才算修到位。
另一条更快的运行时判据：开机日志里必须出现 `insmod crc16:` 这一行
（旧产物压根不打这行），且 `[persist] mount RC=0`。
