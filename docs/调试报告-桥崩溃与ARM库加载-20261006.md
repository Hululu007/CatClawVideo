## 三、ARM 加密库（FishGuard）加载受阻 —— 🔴 已定性，待决策

- **现象**：壳 init 时 `[Init] FishCrypto SO load failed: /thunder/data/fishso/libFishGuard-v8-cl*.so
  UnsatisfiedLinkError: dlopen failed: "…" is for EM_AARCH64 (183) instead of EM_X86_64 (62)`，
  ⇒ 所有依赖该加密库的站点 homeContent 返回空（`分类为空`、`站点推荐暂无内容`）。
- **已排除**：
  - 网络没问题：guest 内 `curl --resolve` 直连 wogg.live（Cloudflare）**HTTP 200**；
    dnsshim 正常出真 IP。
  - native bridge 本体没问题：`LoadNativeBridge=1 / PreInitialize=1 / Initialize=1`，
    artlaunch 审计 `NativeBridgeLoadLibrary(arm64 libc++.so) = OK`（translator 能加载 ARM 库）。
  - isSupported 不是闸门：`NativeBridgeItf+0x20`（isSupported 槽）= `0x1a4a90` = **恒返 1**；
    另有一路径判定函数 `0x1a4b70` = `strstr(path, "/lib/arm")`（常量在 vaddr 0x67dde），
    但 isSupported 恒 1 ⇒ 路径启发式不是本次的闸门。
  - ndk_translation 的 `loadLibrary`（`NativeBridgeItf+0x10` → `0x1a49b0`）无路径检查，
    直通 `GuestLoader::DlOpenExt`（ARM linker）。
- **未解之谜**：NB 已初始化 + isSupported=1 的前提下，该 System.load 仍走了原生 bionic
  linker（错误文本是 bionic 的 EM 对比）⇒ ART 13 的 System.load 路由还有一层我们没摸到的
  闸门（候选：`java_vm_ext.cc` 里对 needs_native_bridge 的判定不止 isSupported 一处；
  或 libart 的 PLT 解析没经过我们的 LD_PRELOAD 垫片——垫片在 default namespace，
  libart 在 ART apex namespace）。垫片里的 `NativeBridgeIsSupported` 钩子（0x5d40，已导出）
  实测未被调用，可作为下一步的探针：加一行 stderr 日志即可判断钩子是否被调。
- **可行方向（供爬虫线决策）**：
  1. **探针优先**：给垫片的 NB 钩子加 `PROPFIX_DEBUG` 门控日志，确认 ART 是否调用它
     （一次重建+重启即可）；不调 ⇒ 换 libart 侧的路由点。
  2. **绕过 ART 路由**：壳侧改为「下载 ARM so → 用 `ndk_translation_program_runner` 以
     **可执行**方式跑解密助手（stdin/stdout 协议）」——绕开进程内 dlopen 的整个问题域；
     这是本项目已验证的 ARM 代码执行形态（harness 同款）。
  3. **patch ndk_translation**：把 `GuestLoader` 的依赖搜索路径加上 /thunder（二进制补丁，重）。
- **顺带修好**：proppreload 的 adbd fork 白名单首次进镜像 ⇒ adb 全程可用（本轮取证全靠它）。
